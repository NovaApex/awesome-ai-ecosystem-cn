# manage-skill — github.html 项目索引管理

## 管理对象

`D:/Project/workbuddy/github-manager/github.html`（GitHub 项目中文速览索引，单文件 HTML，含搜索/分类导航/折叠详情）

## 页面结构资产地图（改动前必读）

github.html 除条目外含以下"结构资产"，均为已确认的改动成果，**日常落库一律不碰**；调整需单独提案并经用户确认：

| 资产 | 位置 | 说明 |
|---|---|---|
| `<style>` 样式块 | `<head>` | 全部页面样式，含速览卡 `.weekly`、NEW 徽标 `.nb`、新条目描边 `.isnew`、chip 日期 `.d`、`details` 的 `scroll-margin-top:72px` |
| 搜索脚本（第 1 个 `<script>`） | `</body>` 前 | 分类导航生成、分区折叠、搜索过滤、锚点 flash 高亮、返回顶部 |
| 本周新增速览脚本（第 2 个 `<script>`） | `</body>` 前 | 读 `data-added` 自动渲染速览卡（自然周口径、今天/昨天/周X 日期标签）+ NEW 徽标 + chip 点击接管跳转 |
| `<div id="weeklyNew" hidden>` | 顶部 blockquote 之后 | 速览容器，内容全由脚本填充 |

⚠️ **已知坑——折叠条目的锚点跳转**：指向 `<details>` 的裸 `href="#id"` 锚点，会在目标因分区折叠而 `display:none` 期间执行浏览器滚动，导致跳转失败（目标滚不到）。页面内一切指向条目的链接必须走"先展开、再 `scrollIntoView` 平滑滚动"的接管模式（速览脚本内已有现成实现，新增此类链接时复用该逻辑）；指向分区标题（`#cat-*`）的锚点不受影响。

## 统一格式规范（入库条目必须遵守）

每条记录 = 一个 `<details>` 折叠块，放入对应分类分区 `<section class="cat">` 内：

```html
<details id="英文短横线slug" data-cat="分类key" data-name="项目名" data-repo="owner/repo" data-added="YYYY-MM-DD" data-blurb="一句话钩子">
<summary><b>项目名</b> · <a href="https://github.com/owner/repo"><code>owner/repo</code></a> — 一句话钩子</summary>

<ul>
<li><strong>定位</strong>：…（详情展开，首句不复写一句话钩子）</li>
<li><strong>能力/特性</strong>：…（可用 <code>code</code> 分隔的特性清单）</li>
<li><strong>用法</strong>：…（CLI / 配置 / 安装命令，命令放 <code>code</code> 或 <code>pre</code>）</li>
<li><strong>要点</strong>：…（License、Star/Fork 等统计数据需注明取数日期、收录日期、坑与注意事项）</li>
</ul>

</details>
```

硬性要求：
1. `id` 为英文短横线 slug，全文件唯一（重复会被搜索脚本覆盖）
2. 五个 data 属性缺一不可：`data-cat` / `data-name` / `data-repo` / `data-added`（收录日期，供"本周新增"速览使用）/ `data-blurb`；**旧条目不强制回填 `data-added`**，仅在下次更新该条目时补上
3. 分类 key 只有 5 个：`dev`（🛠️ AI 开发工具与运行环境）、`tool`（🧰 领域专用工具）、`skill`（🧩 Agent 技能、插件与组件）、`plat`（🌐 平台与框架）、`learn`（📚 学习资料与方法论）
4. 新增/删除条目后，必须同步更新：对应 `<h2>` 里的分类计数、顶部 `<blockquote>` 里的总数；「🆕 本周新增」速览行由页面脚本根据 `data-added` 自动渲染，**无需手工更新**
5. 其他部分（`<style>`、两个搜索/速览脚本、`<footer>` 维护说明）不要改动

## 提问式确认规则（贯穿所有写操作，最高优先级）

**未经用户明确确认，禁止写 github.html。** 每个待确认条款单独列出、用选项式提问（1/2/3 或 A/B/C）逐一确认，禁止 AI 自行猜测或合并省略。标准确认清单：

| # | 待确认条款 | 提问时机 |
|---|---|---|
| 1 | 已收录项目：**不动** 还是 **对比更新**？ | 查重命中后 |
| 2 | 分类归属（拿不准时给 2–3 个候选分类让用户选） | 调研完成后、提案时 |
| 3 | 插入位置（默认建议：同赛道相邻条目之后，说明理由） | 提案时 |
| 4 | 条目全文（新增或更新后的完整 HTML 块） | 提案时 |
| 5 | 对比更新场景：具体增改字段清单（如"补 star 数 / License / 取数日期"） | 更新提案时 |

用户简短肯定（"确认 / 可以 / 同意 / 按需要执行"）即视为通过；用户未回应的条款视为**未通过**，不得落库。

## 备份保留策略

1. **备份位置**：`.workbuddy/backups/backup-<slug>-<当日日期>/github.html`（持久目录，不随 tmp 清理丢失），每次写 github.html 前必须先备份。
2. **重名禁止覆盖**：同 slug + 同日期已存在同名目录时，目录名追加序号（`-2`、`-3`…），防止丢失已有回滚点。
3. **备份后校验**：核对源文件与副本大小一致；不一致立即报告并重新备份，不得继续写操作。
4. **只保留最近 3 份**（按目录修改时间排序）：超出时列出待清理目录（路径 + 备份日期）**请示用户**，AI 不得擅自删除；用户可一次性批量确认，逐个执行，任一次失败立即停止。
5. **标准回滚流程**（用户要求撤销/回滚时）：
   - 列出全部可用备份（路径 + 备份日期）供用户选定；
   - 恢复前先把当前 github.html 另存为 `backup-pre-rollback-<日期>/`（防回滚错误不可逆）；
   - 用选定备份覆盖 github.html；
   - 快速校验（details 开闭数量、总数声明一致）并汇报恢复到了什么状态。
6. 工作区根目录散落的历史备份（如 `github.backup*-<date>.html`）**不属于本 skill 管辖**：不移动、不删除、不重命名，仅在用户主动要求整理时协助。
7. `remote-github.html`（镜像副本）同样不属于本 skill 维护范围，落库后**不做自动同步**；如需同步由用户明确提出。

## 本周新增速览

顶部速览行由页面脚本读取条目的 `data-added` **自动渲染**（**自然周口径：本周一 00:00 本地时间起收录的条目有效**，按收录时间倒序，条目自带绿色 NEW 徽标与描边高亮，周一自动清空重来），AI **无需也不得手工维护速览行内容**。

维护规则：
1. 落库新增条目时，必须带正确的 `data-added="YYYY-MM-DD"`（当天日期）——这是速览的唯一数据源。
2. 不改动 `<div id="weeklyNew">` 容器及其配套渲染脚本；日期过期、列表刷新均由脚本自动完成。
3. 仅"新增收录"进入速览；**对比更新已有条目不计入**。
4. 给旧条目回填 `data-added` 时注意：回填即视为收录、会出现在速览中，日期必须与用户确认，不得估写。
5. 调整速览的渲染脚本或样式不属于常规落库流程，需单独提案并经用户确认。

## 功能 1：GitHub 项目记录

**启动条件**：用户提及"记录"某项目，或直接给出 GitHub 项目地址（`github.com/...`）。

**步骤**（顺序强制，禁止跳步或调换）：

- **step1 查重**：在 github.html 中搜索该仓库（按 `data-repo`、`data-name`、正文关键词）。**查重必须最先执行，查重通过前不得开始调研**，避免浪费。
  - **不存在** → 进入 step2。
  - **已存在** → 走「已收录分支」：
    1. 告知用户已收录（指出条目 id 与所在分类）。
    2. 请求用户许可后，快速对比现有条目与最新数据（Star/Fork、License、最近推送、新增能力等）。
    3. 按「提问式确认规则」#1 和 #5 提问：不动 or 对比更新？更新哪些字段？
    4. 用户选择更新并确认后 → 走 step4（备份）→ step5（更新落库）→ step6；选择不动 → 结束。
- **step2 调研**：访问项目地址，读取 README、License、Star/Fork 等关键信息（网页 + GitHub API 双源核验优先）。
- **step3 提案**：按「统一格式规范」生成完整条目，**展示给用户**：条目全文 + 分类建议（含理由，拿不准给选项）+ 插入位置建议。按「提问式确认规则」#2/#3/#4 逐项确认。**此步只展示，不写文件。**
- **step4 备份**：确认通过后、写文件前，复制 github.html 到 `.workbuddy/backups/backup-<slug>-<当日日期>/`（重名追加序号，禁止覆盖），并校验备份完整（见「备份保留策略」）。
- **step5 落库**：插入条目、更新分类计数与总数；完成后汇报改动摘要（插入位置、计数变化）。
- **step6 审查**：落库后**必须自动执行功能 2** 的质量审查，输出审查结果。

## 功能 2：github.html 内容质量审查

**启动条件**：github.html 内容发生改变（新增/修改/删除条目）之后启动；由功能 1 step5 落库后自动触发。

**步骤**：
- **step1**：阅读 `references/gate.md`，明确审查标准。
- **step2**：按 gate.md 标准对本次变更内容逐项审查，输出审查结果（通过 / 问题清单及修改建议）。
